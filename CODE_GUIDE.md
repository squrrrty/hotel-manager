# Как объяснить проект и изменения

## Общая цепочка

Браузер отправляет HTTP-запрос → Flask выбирает маршрут из `routes` →
маршрут читает форму и обращается к моделям → SQLAlchemy выполняет запрос
в PostgreSQL → Jinja2 подставляет данные в HTML → браузер показывает страницу.
`create_app()` в `app/__init__.py` собирает приложение и регистрирует Blueprints.
Blueprint — просто группа маршрутов одного раздела.

## Подбор номеров: app/routes/rooms.py, list_rooms()

Поля формы отправляются методом GET и видны в адресной строке.
`date.fromisoformat()` переводит строки в даты. Если выезд не позже заезда,
показывается ошибка и пустой результат.

Условие пересечения двух периодов:

```python
Booking.check_in < check_out
Booking.check_out > check_in
```

Обе части должны выполняться одновременно. Бронь с выездом 25 октября
не мешает новой брони с заездом 25 октября. Учитываем только `created`,
`confirmed`, `checked_in`; отменённые и завершённые брони не мешают.
`exists()` отвечает: есть ли у номера такая бронь? `~conflict` означает
«такой брони нет». Фильтр выполняется в БД одним запросом.
Текущий статус `repair` исключается, потому что срок окончания ремонта неизвестен.
Кнопка передаёт `room_id`, `check_in`, `check_out` в URL формы бронирования.

## Создание брони: app/services/booking_service.py

`create_booking()` повторно проверяет даты, существование гостя и номера,
ремонт и занятость. Проверка на сервере нужна даже при наличии JavaScript:
запрос можно отправить напрямую, а доступность могла измениться.
`with_for_update()` блокирует строку номера до конца транзакции PostgreSQL:
если два администратора одновременно бронируют один номер, проверки идут
по очереди. `db.session.add()` готовит запись, `commit()` сохраняет её.
При ошибке маршрут вызывает `rollback()`, чтобы отменить транзакцию и снять блокировку.

## Стоимость: app/models/booking.py и app/static/js/app.js

Свойство `nights` вычитает даты и берёт количество дней.
`estimated_total` умножает ночи на `base_price` категории.
В БД цена хранится как Numeric, в Python это Decimal: удобно для денежных сумм.
Новых колонок нет: оба свойства вычисляются при обращении.

В браузере JavaScript слушает события `input` и `change`, читает даты
и `data-price` выбранного option, пересчитывает подсказку. Число миллисекунд
в сутках — 86400000; ISO-даты Date.parse интерпретирует как UTC.
`setCustomValidity()` показывает ошибку некорректного периода.
`textContent` безопасно обновляет текст, `Intl.NumberFormat` форматирует сумму.
Если JavaScript выключен, бронирование и серверный расчёт всё равно работают.
Это оценка по текущему тарифу, а не модуль платежей или сохранённый счёт.

## Заезд, выезд и уборка

`app/routes/bookings.py`: заезд меняет бронь на `checked_in`, номер на `occupied`.
Перед этим проверяются даты, готовность и отсутствие другого заселённого гостя.
Выезд меняет бронь на `checked_out`, номер на `cleaning`.
`ready()` в `app/routes/rooms.py` принимает только POST и только статус `cleaning`,
затем сохраняет `free`. Редактирование номера не позволяет обойти процесс заезда.
Отменить бронь можно только до заселения.

## Поиск и оформление

`guests.py`: `ilike` ищет подстроку без учёта регистра PostgreSQL, `db.or_`
объединяет поиск по имени, телефону и почте. SQLAlchemy передаёт значения
как параметры запроса. `bookings.py` добавляет условие выбранного статуса.

`base.html` содержит общий каркас и меню. `request.blueprint` определяет активный
раздел. Шаблоны наследуются от base через `extends`, `block content` задаёт содержание.
Фрагмент `bookings/status.html` выводит одинаковые подписи статусов в разных местах.
`style.css` задаёт цвета, карточки, таблицы, формы и адаптацию через `@media`.
Bootstrap остался основой. Новых UI-библиотек, SPA и сборщика нет.
Подписи связаны с полями через `for`/`id`, при ошибках значения берутся из request.form.

## Исправления без миграции

В Room добавлена ORM-связь `bookings`, обратная к Booking.room.
Раньше удаление номера обращалось к отсутствующему атрибуту.
Это связь Python-классов по существующему внешнему ключу, таблицы не менялись.
В config явно выбран `postgresql+psycopg2`, поскольку драйвер psycopg2 уже есть
в requirements. Так запуск не зависит от драйвера по умолчанию новой SQLAlchemy.
Неиспользуемый дубль `app/routes/room.py` удалён: зарегистрирован только `rooms.py`.

## Как показать работу на защите

1. Войти и показать обзор отеля.
2. Выбрать свободный период в «Номерах», перейти к бронированию.
3. Выбрать гостя: показать количество ночей и сумму, сохранить.
4. Попытаться создать пересекающуюся бронь: получить сообщение об ошибке.
5. Для брони на сегодняшнюю дату: заселить → оформить выезд → завершить уборку.
6. Найти гостя по телефону и отфильтровать завершённые брони.

Логика ролей осталась как в MVP: строгого разделения прав admin/manager/maid нет.
Услуги, платежи и публичное бронирование из старого roadmap не добавлялись:
здесь две основные функции и небольшие улучшения ежедневных операций.

## Подготовка к хостингу

Gunicorn импортирует объект `app` из `run.py` и обслуживает HTTP-запросы.
`start.sh` сначала применяет миграции, а затем запускает Gunicorn.
В `config.py` APP_ENV определяет production, а DATABASE_URL и SECRET_KEY
приходят из настроек хостинга. `.env` остаётся локальным файлом.
`csrf.py` создаёт случайный токен в сессии. Каждая POST-форма отправляет его
скрытым полем. Сервер сравнивает токены перед выполнением маршрута.
В тестовых сценариях CSRF отключён явно; отдельный тест проверяет защиту.
На хостинге seed.py получает пароль из ADMIN_PASSWORD и не добавляет демо-бронь.
Подробный порядок: DEPLOY.md.
